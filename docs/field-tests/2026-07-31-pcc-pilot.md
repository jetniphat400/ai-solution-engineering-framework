## Friction log (18 findings, verbatim)

1. Path/version mismatch: the task's given framework-source path pointed to a folder literally named `-v0.1`, whose own `VERSION` file said `0.1.0`. No v0.2 build existed on disk at that path.
2. The specific file the task named, `.claude/skills/engineer/modules/setup-preflight.md`, did not exist anywhere in that source tree — no `engineer` skill, no `modules/` layout pattern existed in that codebase version at all.
3. Because of #1/#2, the task's own diagnostic questions ("does it produce its status vocabulary?", "does it handle the upgrade case?") were unanswerable — there was nothing to observe.
4. Incomplete v0.1 install discovered in the target: skills/agents/rules that `CLAUDE.md` assumes exist were never copied, so following `CLAUDE.md`'s own instructions would have silently done nothing.
5. `AGENTS.md` placeholders were never configured post-install, so any policy reading project-specific fields (risk tier, protected paths, commands) had nothing concrete to check against.
6. `.claude/settings.json` (permission deny rules) was never installed either — the target only had pre-existing `launch.json`/`settings.local.json`, unrelated to the framework.
7. `setup-preflight.md` checks source completeness but not target pre-existing-install state — the upgrade scenario this task specifically asked about is invisible at that stage; the agent has to already know (from outside the module) that the target has old files.
8. The module's `{FrameworkSourcePath}` default ("current repo if already running from it") doesn't cover a third-location agent topology — the actual shape of this session (agent running from target, source in a third location).
9. Confirmation semantics for `setup-preflight.md` step 1 are underspecified: no distinction between "user already told me the target in this conversation" vs. "user must be asked again right as this module executes."
10. (Process, not module) The original task's framework-source path was stale by one relocation and one version — cost a full round-trip before the real `setup-preflight.md` was even reachable. A real-world "the map is out of date" failure mode this framework will hit often, given it explicitly targets inherited/drifted repos.
11. Verified installer-script defect: `Copy-Item -Recurse -Force` (PowerShell) and `cp -R` (bash) both nest a source directory inside an existing destination of the same name rather than merging/replacing it (confirmed empirically in an isolated test). This makes `install-to-project.ps1`/`.sh` unsafe for exactly the case this whole exercise is about — installing onto a repo that already has `ai-engineering/`/`.claude/` from a prior version. `setup-install.md`'s "Installer script" option is not actually usable for upgrades as-is.
12. `setup-install.md`'s conflict language only names `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json` for "don't overwrite without reviewing/merging" — it never mentions `ai-engineering/` (a directory that clearly can conflict) or the fact that `.claude/` is not atomic (it can contain a mix of framework and non-framework content needing different treatment per subpath). The module's four-item framing broke down in practice; decomposing `.claude/` into six sub-decisions was necessary and not guided by the module.
13. The source repo ships `.claude/skills/engineering-workflow/SKILL.md` as a full undeclared duplicate of functionality the new `engineer` skill's ROUTE table already covers — no alias note (unlike `redteam`, which correctly self-declares as a thin alias), no deprecation marker. A real ambiguity the module gave no guidance on; required a human decision (resolved: skip it).
14. The source repo's own `VERSION` file still reads `0.1.0` despite 10 commits of "Round 1/Round 2" feature work (the `/engineer` skill, setup modules, redteam module) sitting on top of the `60602f9` baseline — there's no version bump marking this as "v0.2," which is the label used throughout this task. Worth fixing in the framework repo itself so future installs aren't guessing at version identity from git log depth.
15. `setup-configure.md`'s step-1 placeholder inventory has no slot for project conventions, yet `AGENTS.md`'s own "Required behavior #6" assumes such conventions exist somewhere project-specific. A `## Conventions` section was added outside the module's stated scope to fit the real facts supplied.
16. The human-supplied "build/format/lint/type-check: `[NOT CONFIGURED]`" claim was only true for the backend — the frontend has real `build`/`lint` scripts (`package.json`, `eslint.config.mjs`). The module's own "verify with evidence" instruction caught this; trusting the claim as given would have shipped an inaccurate contract on day one.
17. "Default risk" being hard-flagged as never-guess (even with strong technical evidence pointing one way, via `risk-classification.md`'s auth-bypass rule) worked exactly as designed — it correctly forced a stop-and-ask rather than a silent derivation.
18. `setup-configure.md`'s written procedure never mentions `.claude/settings.json` at all — reviewing/extending its deny rules was something the human had to ask for explicitly; it's outside this module's stated scope even though it's clearly part of "configuring the repository contract" in practice.
