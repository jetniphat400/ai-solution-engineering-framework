## 3. What the framework caught (its wins)

### "Identical" claims that did not survive literal re-verification

The register makes this an explicit, tracked discipline rather than an incidental habit: five consecutive dedup candidates (`R7`, `R35`, `R36`, `R37`, `R38`) were each independently re-verified against real code and, for the money-adjacent ones, real market data — not taken on the original audit's word that two implementations were "identical."

- **`R7`** (`adx()` vs shared `atr()`): proved genuinely equivalent — `Series.equals()` True, maxdiff 0.0 across 5 symbols — *before* refactoring, establishing the proof standard later items call "R7-level proof rigor."
- **`R35`** (`_own_risk_reward` vs `generate_trade_plan`'s target formula): re-verification found the two were the same formula *shape* but **not** byte-identical — one rounded its entry midpoint, one didn't — a real discrepancy in 5 of 13 real setup candidates on a 14-symbol basket (magnitude 0.00005-0.0001 THB, below any displayed threshold, but real). Reported as a design question and decided explicitly rather than silently picking a convention.
- **`R36`** (bullish-divergence check in `scanner_technical.py` vs `setups.py`) — the register's own text calls this the **"third audit 'identical' claim in a row... to fail literal re-verification once input provenance was checked, not just formula text"**: the swing-point input was identical, but the RSI input came from two different computation families (unrounded vs. rounded 2dp). The `>30` boundary decision never actually flipped across 14 real symbols, but the provenance gap was real and was resolved by an explicit decision (point both call sites at the same rounded value), not assumed away.
- **`R37`** (journal/alerts insert-then-fetch pattern): re-verified anyway per the same pattern — this one **held up**, genuinely identical, extracted cleanly.
- **`R38`** (dividend-yield/debt-to-equity duplication): required a *history-aware* re-check against three prior fix commits (`ISSUES.md #1`, `#26`, `#32`) before concluding the duplication was real and safe to extract — one adjacent-looking field (`roa`) was confirmed **not** part of the same duplicated block by design, not by oversight.

Net effect: of five "these look identical" candidates put through literal re-verification, one (`R37`) confirmed true as originally stated; the rest surfaced a real, previously-unrecorded gap that the campaign then had to make an explicit, evidenced decision about rather than silently resolve.

### Misattribution caught mid-campaign, corrected before it propagated

`R33`'s investigation notes an earlier pass through the same file had mis-listed `RANGE_SUPPORT_BUY` as using raw (unfiltered) swing points; before that error could feed into Gate 2's real-data study, it was re-verified directly against `_detect_from_bundle`'s code and fixed — in both the register text and the corresponding code comment (`setups.py:73`) — as its own commit, `02b322b`, described as "correction — fixed a setup-type misattribution in the previous commit's own comment/register text before it could feed Gate 2."

### Inventory claims found half-stale

`R41`'s original register text claimed "6 fields never rendered anywhere" on the frontend. Re-verification against current code before touching anything found `roa`, `eps`, and `sector` were **already** rendered — just accessed through an untyped value, so TypeScript wasn't catching a real type-declaration gap underneath them. The real, narrower gap (3 unrendered fields plus missing type declarations for all 6) is what got fixed; the stale two-thirds of the original claim did not get "fixed" because it was never broken.

Separately, `R19` (frontend nav gaps): re-verification during the fix found a **fourth** unreachable route (`/ai`) that the original audit had missed, and folded it into the same fix rather than closing the item against the original, incomplete list.

### A false premise caught before it drove a code change

`docs/ISSUES.md #38` (`routers/plans.py`'s `risk_pct` has no Pydantic-level bound) was investigated on the premise that this meant out-of-range values could reach the service unvalidated. The investigation found the opposite: `trade_plans.compute_position_size`'s own service-level check already rejects the value with a 422 either way — the gap is that the OpenAPI schema at `/docs` doesn't *advertise* the 0-5% constraint, not that the constraint is missing. Severity was downgraded accordingly (documentation/schema-completeness gap, not a validation bug) and no code was changed on the strength of the original framing.

`R10` (`setups.MANAGING`) is the same pattern applied to a bigger item: the register's own proposed action ("clarify the docstring, or wire a UI action") implicitly assumed something was missing or broken; investigation found a fully-wired, DB-enforced, audit-logged, API-reachable state machine that the UI simply chooses not to expose a button for — a deliberate simplification, not a defect. Nothing was wired; only the docstring changed.

### The `frontend/AGENTS.md` false alarm

Resolved during this same window (documented as a "process note, not a finding" directly in the register, cross-referencing report #1's friction #19): a subagent's read-only-audit suspicion that `frontend/AGENTS.md` was a prompt-injection attempt was briefly restated as verified fact across two turns before an explicit user challenge triggered re-verification — which reversed the conclusion completely (genuine `create-next-app` scaffold output, confirmed against `next`'s own bundled docs). Recorded here again because it happened *during* the same operational window this report covers, not just during setup.

## 4. Friction findings

1. **Unverified findings can re-surface as fact across turns/sessions with no confidence label attached.** Already the subject of report #1's friction #19 (the `frontend/AGENTS.md` case) — restated here because the underlying mechanism gap is a property of the *framework*, not a one-off incident, and this campaign is a second, independent occurrence of the same failure mode within the same operational window. Nothing in `/engineer`, `redteam`, or the verification contract requires a claim to carry a `verified`/`inferred`/`flagged-not-verified` tag as it moves from one agent's output into a persisted document or a later turn's restatement.

2. **Audit claims from a prior pass repeatedly failed literal re-verification, with no standing framework rule requiring the re-check.** Five deduplication candidates in a row (`R7`, `R35`, `R36`, `R37`, `R38`) were treated with real-data proof rigor — but that discipline is visible only as an ad hoc pattern the campaign itself adopted and then explicitly named ("R7-level proof rigor," "per the R7/R35/R36 pattern," `REFACTOR-REGISTER.md:153,157,161,164`) as it went, not as a rule stated anywhere in `AGENTS.md`, `ai-engineering/core/*`, or the `/engineer` skill. Four of five "identical" claims needed correction or a fresh design decision once actually checked (§3). A framework that already ships an `engineer` skill and a `redteam` skill has no named place for "an audit claimed X is identical/dead/unused — do not act on that claim until re-derived from current code and, where money/scoring is involved, real data."

3. **The Gate pattern (investigate → approve → study → decide) has no name or template in the framework, despite doing real work twice.** `R33` was explicitly split into three gates — Gate 1 (execute under Standard lane, tests first), Gate 2 (study only, no code, a persisted reusable script), Gate 3 (the actual structural decision, evidence-based rejection) — and the money-path batch used the same investigate-then-gate-approval shape for all five of its items. This produced a real, traceable "we looked before we leaped, and the numbers said no" outcome (Gate 3's rejection, backed by Gate 2's data) rather than either blind action or blind inaction. Nothing in `ai-engineering/core/workflow.md` or the `engineer`/`redteam` skills names this as a repeatable procedure with its own vocabulary (e.g., "investigation gate," "study-only gate," "decision gate") — it was invented fresh, mid-campaign, and would have to be reinvented by the next campaign that needs it.

4. **`PCC_AUTH_DISABLED=1` was used for local verification with no framework guidance on temporary-bypass hygiene.** `R41`'s proof step started the dev servers with `PCC_AUTH_DISABLED=1` to call live endpoints, then stopped the servers afterward (`REFACTOR-REGISTER.md:182`, "Dev servers stopped after verification.") — handled responsibly *this time*, but entirely by ad hoc discipline. `AGENTS.md` names `PCC_AUTH_DISABLED` handling in `main.py` as a protected asset (auth-bypass flag, `docs/ISSUES.md #10`) but has no stated rule for the adjacent, very-likely-to-recur case: temporarily *using* that same flag as a verification tool. There is no guidance on always shutting it back off, never leaving a server running with it set, or logging when/why it was enabled for a session — the kind of hygiene gap that matters precisely because the flag is already flagged elsewhere as a real, standing HIGH-risk defect (`docs/ISSUES.md #10`).

5. **The campaign's own completion tracking never uses the framework's mandated terminal status vocabulary.** `AGENTS.md`'s "Completion status" section requires ending with exactly one of `DONE_VERIFIED`/`CONDITIONAL_PASS`/`REPLAN_REQUIRED`/etc. Report #1 uses these terms for its three setup modules. The 56-item register and the five `ISSUES.md` money-path entries instead use a parallel, locally-defined legend (`DONE`/`OPEN`/`NEEDS DECISION`/`CONTESTED`) that is never mapped back onto the framework's vocabulary anywhere in either document. Both legends express real verification discipline, but a reader (or a future automated check) looking for `AGENTS.md`'s contractually-required status string on any of these 56 items will not find one — the contract's own terminal-status requirement is silent on how it composes with a large, multi-item, multi-session register rather than a single task.

6. **Lane classification for the 56 register items is evidenced only by its output, not by any recorded classification step.** Every item carries a `Lane:` tag, and Controlled-lane items visibly got the extra approval-gate treatment Standard-lane items didn't (§2) — but neither `REFACTOR-REGISTER.md` nor `ISSUES.md` records *how* each tag was assigned (an `/engineer` invocation, a human call, or something else), and no per-item classification rationale survives the way, e.g., `R32`'s full investigation-before-decision does. This means the campaign's lane assignments cannot themselves be audited for consistency after the fact — only trusted on the strength of the visibly-different rigor applied to Controlled vs. Standard items.

7. **A large findings register with a local numbering scheme risks colliding with the framework's own permanent issue register, and did.** `REFACTOR-REGISTER.md:5` documents that the original informal delivery used bare numbers (`#37`-`#87`) that later collided with real, already-committed `ISSUES.md` issue numbers once five of them were formalized — requiring the entire register to be renumbered onto a separate `R`-prefixed scheme specifically to avoid cross-referencing ambiguity. This is a real process hazard (two parallel numbering spaces for findings, one of which the framework already treats as authoritative per `AGENTS.md`'s "`docs/ISSUES.md` is the single verified issue register") that the framework gives no guidance on avoiding when a large audit produces more findings than fit comfortably as `ISSUES.md` additions.

## 5. Verdict

**What v0.2 proved in operation.** Run for real, at scale (56 findings, 40 executed, three lanes, a single ~6h continuous session), the framework's core discipline held under load rather than only in the small install-time checks report #1 exercised: Controlled-lane items got real pre-code diff approval and landed with the heaviest test coverage of the campaign (10 new tests for the Settrade ceiling alone); "verify before acting" was not just followed but actively caught real, previously-unrecorded gaps five separate times on claims that looked safe to act on blind (§3); and at least twice (`R10`, `ISSUES.md #38`) the discipline stopped a proposed fix outright because investigation found nothing to fix. The framework's instruction to classify risk and lane, and to require evidence before closing an item, is doing real work here — this was not a paperwork exercise layered on top of changes that would have happened the same way regardless.

**What the friction list implies for the next version.** All seven items above are gaps in *coordination and vocabulary*, not gaps in the underlying judgment the campaign exercised — the campaign's operators invented working solutions to five of these (the re-verification discipline, the Gate pattern, the responsible-but-undocumented `PCC_AUTH_DISABLED` handling) without the framework naming or requiring any of them. That is the clearest signal from this field test: the next version should promote at least two of these ad hoc inventions into named, reusable framework concepts — a confidence-label convention that survives claims being summarized or repeated (friction #1, and report #1's #19), and a named Gate procedure (friction #3) — and should resolve the vocabulary mismatch between a project's own large-scale tracking documents and the framework's single-task terminal-status contract (friction #5) before a third campaign has to invent its own third convention.
